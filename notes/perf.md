# Performance: measurements, hitches, fixes, smooth simulator recording

Measured on 31/10 (agent PERF) on a dedicated sim "Neon Perf 17 Pro Max" (`A2983920-E64C-42E0-AFD5-06829B47984E`,
1320×2868), Mac M5 Pro. The simulator runs at **60 Hz** (the sim's CADisplayLink doesn't go up to 120).

## TL;DR

1. **The bottleneck is the GPU, not JS or the UI thread.** Time Profiler (lights on): main thread busy ~9 % (~1.8 ms/frame,
   mostly Dawn/Metal encode), JS thread a steady 60 fps. Frames drop because the GPU can't keep up.
2. **Culprit #1: `BlurMask` on paths redrawn every frame** — the σ18 + σ6 glow of each tube segment (`UnitLit`) costs
   **~52 ms GPU/frame**, glass + shadow (inner blur + σ2.6) add ~13 ms. Wall/puddle/steam shaders are only 3–5 ms per layer.
3. **Fix:** bake glow/shadow/glass rim **once** into a raster image when the tube is created; each frame just draws the image + tints
   it → glow drops to **<1 ms**. Whole frame (GPU, same load): **130 ms → 9.4 ms** (run 2; run 1: 79 → 31 ms).
   Ready diffs: `notes/perf-diffs/1-tube-baked-glow.diff` (Tube.tsx), `2-shaders.diff` (wall.ts, post.ts).
4. **Recording:** the machine is running 7 simulators + 3–4 Blender processes (load average 300–800) → that load makes the clip
   stutter more than the code does. See "Smoothest simulator recording".

## Proposed fixes (by benefit)

### 1. Bake glow, shadow and glass rim (`src/neon/Tube.tsx`, agent M4) — `notes/perf-diffs/1-tube-baked-glow.diff`

Full version already tested: `app/src/perf/variants/TubeFast.tsx` (same exports, same props, drop-in replacement).

- `UnitLit`: the σ18 + σ6 glow is drawn **once** (white, 1.5 px/pt, `Skia.Surface.MakeRaster` like `atlas.ts`) in
  `useMemo([unit.path, w])`. Each frame only draws one `<Image>` + `<BlendColor mode="srcIn">`. Glow colour = mix of old →
  new colour by that segment's `split`, so when the gas colour change flows along the tube the glow still changes letter by letter. The sharp colour layer + core are still
  trimmed paths (no mask filter), so the gas edge stays exact.
- `TubeShadow` / `TubeGlass`: during the 0.35 s a tube is "freezing" they still draw live paths; afterwards they switch to the baked image (shadow
  2 px/pt, body + inner-blur rim 3 px/pt). The gyro highlight stays a live path (no blur).
- `TubeFreeze` and the gas-edge streak: zero-length path when idle (previously still drew a blurred segment at opacity 0).
- Cost: baking runs on JS when a tube is committed, a few ms per segment (CPU), no effect on the UI thread.

### 2. Shaders (`src/shaders/wall.ts`, `post.ts`, agent M4) — `notes/perf-diffs/2-shaders.diff`

- **W1** `atlasFn`: skip atlas tiles whose 3 cells are all off (uniform branch; the demo only uses 2–3/4 tiles, 0 with lights off).
  No visual change. Steam benefits too since it shares the function.
- **W2** puddle: wall reflection = `lightAt(q) · albedo · gain · 0.8` instead of the full `surf(q)` (2 fewer atlas
  reads for the gradient, no normal/data reads).
- **W3** tube reflection: 2-tap vertical blur (±s/2) instead of 3 taps.
- **P1** steam: compute `band` first, return early outside the steam band (top half of the screen skips 15 noise calls).
- **P2** steam: domain warp uses 3-octave fbm (low frequency, no visible difference).

### 3. Smaller items (no diff yet)

- `Decor.tsx` (`WireLine`, `TubeLink`): wire shadows and blockout shadows are also per-frame `BlurMask` (σ1.6 / σ2.6). Few paths so
  much cheaper than the glow, but they can be baked the same way as `TubeShadow` in `TubeFast.tsx` if a few more ms are needed.
- `NeonScene.tsx` (stroke being drawn): the chalk trail behind the finger has `BlurMask 5` on the whole stroke (≈10 ms GPU once the "hello" stroke is
  complete) and the pen-tip dot `BlurMask 6`. Only runs while writing (1.5–6.6 s of the demo), but that's exactly the shot where the camera pushes in on the
  finger. Proposal: replace the path blur with 2 unblurred strokes (measured ≈0 ms):
  ```tsx
  <Path path={livePath} style="stroke" strokeWidth={liveW14} strokeCap="round" strokeJoin="round" color="rgba(255,226,244,0.12)" />
  <Path path={livePath} style="stroke" strokeWidth={liveW7}  strokeCap="round" strokeJoin="round" color="rgba(255,226,244,0.2)" />
  // liveW14 = brushW·2, liveW7 = brushW; the pen-tip dot (Circle, 1 small circle) can keep BlurMask since it's very cheap
  ```
- Assets: `normal.png` 4.5 MB and `data.png` 2.2 MB (8-bit RGB, 1320×2868). Lossless WebP only saves 17–26 % and needs path
  changes in code; images are decoded only once at app launch (the scene clock starts only after they load), no effect
  on smoothness → **no compression**, keep as is. For faster app launch: change `save()` in `render_passes.py` to export lossless
  WebP; don't compress by hand since `tools/build.sh` will overwrite.
- Tried "run heavy passes at lower resolution" for steam: no gain (see table). The wall shader has normal-map detail so it
  can't be lowered. So caching blur results is the main lever.

## Smoothest simulator recording

By impact (measured: same build, same scene, UI fps fell from 50–58 to 3–36 when the machine was loaded with
Blender + many sims):

1. **Apply diff 1 (pre-baked glow)** before recording the final. It's the only code that pushes the GPU past the 16.7 ms budget.
2. **Free up the Mac's GPU while recording** (the simulator draws with the Mac's real GPU via `SimMetalHost`):
   - Pause all Blender renders: `PAUSE_PATTERN="Blender -b" tools/promo.sh …`. `promo.sh` will `kill -STOP` and then
     `-CONT` after recording. This pattern also pauses other projects' Blender, so give notice, or use
     `PAUSE_PATTERN="neon.blend"` if only neon renders may be paused.
   - Shut down unused simulators (`xcrun simctl shutdown <udid>`), especially sims running animated Skia apps (Neon B,
     Neon Perf, Pumpkin …). At minimum quit the app on those sims: every continuously animating app competes for the GPU.
     My perf sim quits the app after each measurement.
   - Don't run `expo run:ios` / `xcodebuild` in parallel while recording.
3. **Use the Release build** (`--configuration Release`, `EXPO_PUBLIC_DEMO=1`, **no** `EXPO_PUBLIC_PERF`). Don't record the
   Debug build, since RN/Reanimated C++ runs at -O0. A rebuild is needed to get expo-audio: the current Release build (14:38) lacks
   that module so `initAudio` will error.
4. Plug in the charger, turn off Low Power Mode, keep the Simulator window visible on screen (not minimised, not in another Space).
5. After recording: `promo.sh` already conforms to 60fps by pts. Check dropped frames with
   `ffmpeg -i render/promo/raw.mov -vf mpdecimate -loglevel debug -f null - 2>&1 | grep -c drop`
   (number of duplicate frames). To know the app's fps during recording, record once with the overlay (perf build).
6. The sim is 60 Hz so 120 Hz ProMotion doesn't matter for recording. A real iPhone 17 Pro Max will run at 120 Hz; then
   the budget is only 8.3 ms/frame, so diff 1 matters even more.
